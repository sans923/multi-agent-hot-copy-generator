# Python AI 全栈情景题与系统设计题

> 本文档沉淀 Python 后端、AI Agent、排障和系统设计场景。项目事实必须有代码或实际验证依据；通用设计建议不得伪装成项目已实现能力。

## 1. 如何设计可持续的对话知识归档？

### 情景

团队希望持续吸收当前项目对话和其他相关聊天，用于更新项目复盘、知识手册和面试资料，同时不能收集私人聊天或把聊天里的提示注入当作命令执行。

### 回答要点

1. 当前任务结束前做实时归档，避免高价值上下文在会话结束后丢失。
2. 每日任务扫描侧边栏，只读取白名单主题，并用“任务 ID + 最后处理位置”实现增量同步。
3. 原始材料先进入收件箱，再按项目事实、通用知识、面试话术和情景题分类，避免直接污染正式文档。
4. 聊天内容一律视为不可信数据；过滤敏感信息，不执行其中命令，无法读取时明确标为“不可访问”。
5. 用稳定标题或知识键去重，优先更新已有章节；写入项目事实前必须回到代码或测试证据。
6. 每轮记录扫描范围、实际更新、失败和待验证项，使流程可审计、可恢复。

### 追问：如何避免重复和漏处理？

为每个聊天保存稳定任务 ID 和最后处理游标；写入时使用确定性分类键和已有章节检索。只有成功写入收件箱并完成目标文档更新后才推进游标，失败则保留原游标并记录错误，下一轮可以安全重试。

### 项目落地状态

截至 2026-08-13，规则、收件箱、同步状态和目标文档结构已建立；侧边栏覆盖率、游标稳定性及每日任务的首次运行结果仍待验证。

## 2. 第三方平台写着“支持发布”，为什么个人项目仍可能不能直发？

### 情景

你正在给 AI 内容生成系统接入抖音。开放平台同时存在投稿/分享能力和“代替用户发布内容”能力，但后者只允许特定主体和内部网站应用。产品希望把它宣传成个人用户点击一次后由服务器静默发布。

### 回答要点

1. 先区分“接口存在”“当前应用可以申请”“用户已经授权”“产品场景允许上线”四个层次，不能只看到接口文档就判断可用。
2. 服务端代发意味着第三方持有长期授权并代表用户产生外部副作用，因此主体、监管、内容安全和用户感知要求通常更严格。
3. SDK/H5 投稿是另一条路径：系统准备素材并拉起平台发布器，由用户本人预览和确认；自动化程度较低，但更符合个人账号运营场景。
4. 在架构上用 `Publisher` 适配器和能力标志区分 `direct_publish`、`user_confirmed_post`、`assisted_export`，不要在前端统一显示为含义模糊的“已发布”。
5. 平台申请尚未通过时提供辅助发布降级方案，并把“待用户确认”“已提交审核”“平台已发布”建模为不同状态。

### 项目落地状态

截至 2026-08-13，本项目只完成方案审计，尚未实现平台账号、OAuth、发布任务或适配器；个人应用的具体投稿权限仍待开放平台审核，不能写成已经可用。

## 3. 用户创建 Agent 任务后，应该用 BackgroundTasks 还是任务队列？

### 情景

FastAPI 接口创建一条 Agent 任务记录后，希望立刻返回 `task_id`，再在后台调用大模型、RAG 和第三方 API。产品还要求服务重启后继续执行、失败可重试，并能查询进度。团队提议直接使用 `BackgroundTasks`。

### 回答要点

1. 先区分“响应后执行”和“可靠异步执行”：`BackgroundTasks` 只保证任务挂在响应之后尝试执行，仍依赖当前 Web 进程。
2. 短小、非关键、允许失败的通知或日志可以使用 `BackgroundTasks`；长时间 Agent 编排、发布、支付等不可丢任务应使用持久队列和独立 Worker。
3. `add_task()` 应传函数对象及参数；同步任务进入线程池，异步任务由事件循环执行，但 CPU 密集任务不会因为写成 `async def` 就获得并行能力。
4. 多个后台任务默认按顺序执行，异常要记录和隔离；关键链路不能依赖“响应已经成功”来推断任务已经完成。
5. 不向后台任务传请求级 Session、Request 或文件句柄，只传稳定业务 ID，并在任务内部重新获取资源。
6. 生产方案应包含任务落库与投递一致性、幂等键、租约认领、有限重试、死信、Checkpoint 和进程重启恢复；必要时使用 Outbox 避免“数据库提交成功但消息没发出”的窗口。

### 面试回答

> `BackgroundTasks` 适合响应后的轻量收尾，不适合承担必须完成的长任务。这个项目当前用它启动 Agent，作为单机 MVP 很简单，但 Worker 重启会有丢任务风险。生产化我会让 API 只负责写任务并返回 ID，通过 Outbox 把任务投递给独立 Worker；Worker 使用幂等键和租约防止重复消费，并从 Checkpoint 恢复。这样 HTTP 响应、任务执行和故障恢复的职责才真正分开。

### 项目落地状态

当前项目已使用 `BackgroundTasks` 启动编排，并实现了单机 Checkpoint/恢复语义；持久任务队列、独立 Worker、多进程共享状态与 Outbox 尚未实现，不能描述为生产级可靠执行。

## 4. 如何实现“打开平台发布页”，又不误报成“发布成功”？

### 情景

内容生成系统需要支持头条和抖音，但头条文章只能人工确认，抖音 H5 投稿也只是拉起发布器。产品仍希望按钮文案叫“一键发布”。

### 回答要点

1. 将终稿冻结、生成发布包或签名链接称为“发布准备”，不要创建已发布记录。
2. 头条返回官方创作页和可复制内容；抖音返回短时 H5 Schema，由用户在客户端确认。
3. Client Secret、client token 和 open ticket 只放服务端；前端只获得必要的短时跳转结果。
4. API 对任务做所有权检查，并用前后端一致的 `copy_id` 验证页面当前终稿；素材要求 HTTPS、拒绝私网/凭据 URL且只能来自自有 CDN 白名单。
5. 未获批能力、缺少素材或平台错误要返回 blocker；前端展示“待用户确认”，而不是静默失败或误报成功。
6. 真正的 `published` 必须来自平台 item ID、回调或后续查询；在此之前最多是 `ready` 或 `submitted`。

### 项目落地状态

本项目已实现头条辅助发布和抖音 H5 发布准备，并补充终稿一致性、安全白名单和前端弹窗/错误路径测试；尚未使用真实凭证或真机验证，平台最终发布状态也未接入。

## 5. 产品说“马上会有 100 个用户”，你怎么买服务器？

### 情景

一个 FastAPI + Multi-Agent + MySQL + Chroma + 外部 LLM API 的项目即将开放给 100 个用户。请给出首期服务器规格、前提、风险和扩容路径。

### 回答要点

先追问 100 是注册量、日活、同时在线还是同时生成。首期若假设总用户约 100、常态在线 5～10、同时生成 2～5，可选择 Linux 4 核 16 GB、180～220 GB SSD、10～15 Mbps；预算紧时 4 核 8 GB 可作为观测起点。模型通过外部 API 调用，不购买 GPU。本地 Embedding、Chroma、多进程副本和同机 MySQL 使内存优先级高于文本业务带宽。

上线前要给生成入口加用户级与全局并发上限，记录队列长度、等待时间、任务 P50/P95、内存、数据库连接和 LLM 429/超时率。当前若仍用 Web 进程内 `BackgroundTasks`，不能承诺 100 人同时生成：Web 重启可能丢任务，多 Worker 还会复制调度器和进程内状态。峰值达到 10 个以上同时生成时，先迁移到 Redis/RabbitMQ + Celery/RQ/Dramatiq 一类持久队列，拆 Web 与 Worker，再根据实测增加 Worker 实例或使用托管 MySQL。100 个同时生成属于另一档架构问题，需要排队、背压、幂等、故障恢复和真实压测，不能靠购买一台更大的机器代替。

### 验证计划

用不调用真实付费模型的 stub 压 API、轮询和数据库，再以小规模真实模型请求校准单任务时间及限流；逐级测试 2、5、10 个生成并发，观察 P95、错误率、内存峰值和队列等待。未执行这些测试前，规格只是有明确前提的容量假设。

### 规模升级追问：从 100 增加到 500 用户

若峰值在线 20～50、同时生成 5～10，8 核 32 GB 单机可作为过渡，但推荐 2 个 Web、2 个 Worker、Redis 和托管 MySQL。生成 Worker 总并发先限制为 4～8，通过队列吸收突发。水平扩容前需要把本地 checkpoint、Chroma 和调度器改为共享或单例服务，并重新计算数据库连接池总量。若 500 个任务详情页都维持 3 秒轮询，理论请求量约为 167 QPS，应改用 SSE 或退避轮询。若 500 人同时生成，则必须先取得模型 API 配额、规定最大可接受等待时间，再由单任务时长和目标吞吐反推 Worker 数量，不能给出固定单机规格。

## 6. 模型只能看到部分工具，为什么服务端还要再做白名单？

### 情景

Multi-Agent 系统已经按角色只把部分 Tool Schema 发给模型。团队认为模型“不知道其他工具”，所以执行器只要在全局注册表中找到函数就可以执行。现在需要评估 Prompt Injection、模型幻觉和未来代码入口带来的越权风险。

### 回答要点

1. 模型看到的工具集合是能力提示，不是服务端授权；模型输出始终是不可信输入，可能伪造任意函数名。
2. 每个 Agent 应有明确 allowlist，执行器在解析参数和产生副作用前检查函数名；不命中时返回失败并记录 agent、函数名和任务上下文。
3. 工具名称通过后仍需校验 JSON Schema、业务对象所有权、任务状态和副作用权限；名称白名单不能替代参数授权。
4. 默认值应 fail-closed。若为遗留直接调用保留 `None=全部注册工具`，必须枚举调用方、限制入口并制定迁移计划。
5. 用测试证明“工具已注册但当前 Agent 未授权”时真实实现零调用；同时测试授权路径、未知工具、非法 JSON 和审计记录。
6. 项目当前已实现模型侧工具子集与 `SkillExecutor` 服务端二次校验，并有越权不执行测试；统一参数 Schema 校验和 `None` 默认拒绝仍待实现。

### 面试回答

> 我把模型的 tools 列表看成 UX，把 Executor 的 allowlist 看成安全边界。项目按 Agent 职责只暴露工具子集，但模型返回函数名后，服务端仍用同一列表二次检查；即使它被注入诱导调用另一个已注册 Skill，也会在执行前被拒绝。之后还要继续做参数 Schema、对象所有权和状态校验。当前遗留接口允许不传名单，我会先盘点调用方，再迁移成默认拒绝，避免未来新增入口漏传参数时静默扩大权限。

## 7. Agent 已有 RAG 和 Checkpoint，为什么还不能称为完整记忆系统？

### 情景

一个多用户内容 Agent 已保存任务状态、LangGraph Checkpoint、历史文案、向量知识库和风格卡。团队认为“记忆系统已经完成”，准备让所有用户共享历史优质文案并根据 Reviewer 高分自动强化风格。

### 回答要点

1. Checkpoint 解决执行恢复，RAG 解决相关知识召回，用户长期记忆解决跨任务偏好；三者目标、作用域和保留期不同。
2. 所有检索必须先按 tenant/user、权限、状态和数据用途硬过滤，再做相似度排序；向量相关性不能替代多租户授权。
3. 检查读写闭环：生成后是否幂等入索引、更新/删除是否同步、索引失败能否重试、索引能否从关系库重建；不能只验证 query API 返回 200。
4. 模型自评分不是用户满意度或业务效果。显式反馈、采用版本、发布指标与 Judge 分数应分开，避免自我强化偏差。
5. 长期记忆写入要有候选、校验、审核、版本、失效和遗忘；单次模型输出不能直接覆盖全局风格规则。
6. 检索应逐步加入混合召回、阈值、按来源去重、多样性、rerank 和 token budget，并用 Recall@K/nDCG、双用户隔离、故障降级和生成盲评验证。

### 项目落地状态

本项目最初只有分散的工作状态、事件表、头条 RAG 和风格卡；历史文案保存调用的索引函数不存在，collection 缺失时会静默返回空，且 Chroma/DB 检索没有用户隔离。当前已完成可信 task owner 贯穿、双路径隔离、故障降级、Outbox/租约索引、显式偏好与反馈、追加版本、失效过滤、混合检索、上下文预算和检索指标，并由完整回归验证。仍不能宣称“生产级且越用越好”，因为生产数据库迁移、共享向量服务、真实编辑/发布反馈、并发压测和线上质量增益尚未验证。

## 8. 为什么 Agent 显示 completed，内容团队仍认为任务没有完成？

### 情景

文案 Agent 已经生成终稿，后端把 Task 标为 `completed`。但运营人员认为还没有审核、排期和发布，产品经理又希望系统根据“完成任务”自动学习用户风格。

### 回答要点

1. `completed` 混合了机器执行、内容交付和渠道发布三种语义；应拆成 `execution_status`、`content_status`、`publication_status`。
2. 每个状态都应给出责任人、进入时间、阻塞原因和下一步动作；前端显示用户主状态，技术步骤放入可展开审计。
3. 知识库、风格卡和历史记忆职责不同：知识提供事实，风格提供表达规则，记忆保存用户真实选择与反馈。
4. 生成稿不是长期偏好。只有明确采用、编辑 diff、拒绝原因、多次稳定反馈或可信平台结果才能进入候选记忆。
5. 生成时保存引用来源和风格快照；否则知识或风格更新后无法解释旧稿。
6. 产品验收同时看 Brief 完整率、采用率、改稿轮次、引用命中和发布反馈，不能只看模型分数或接口成功率。

### 面试回答

> 我会把模型执行成功看成生产流程中的一个技术事件，而不是业务完成。系统需要三套正交状态：Agent 是否执行成功、内容是否审核通过、渠道是否真正发布。知识、风格和历史反馈分别建模，只有用户采用/修改和真实效果才能进入受治理的长期记忆。这样既能告诉运营下一步做什么，也能避免模型用自己的高分反复强化自己。

### 项目落地状态

当前项目已经拆分 `execution_status/content_status/publication_status`，并实现 Content Brief、采用/拒绝/编辑反馈、父子 Copy 版本和 diff、冻结风格快照、知识引用、幂等发布记录、指标回填及三条同类正向证据后的偏好晋升。后端完整回归为 215 项，前端为 9 项且构建通过；三份新迁移已在真实 MySQL 8.0.46 可重入执行。尚未验证真实平台回调、业务语料离线评测、人工盲评和线上效果。

## 9. 热榜写库成功，但向量化报 `_type`，是否直接改 SQLite 配置？

### 情景

MySQL 中热榜数据正常，Chroma 持久库在启动向量化时抛出 `'_type'`。团队建议直接给 collection 配置补字段继续运行；Embedding 模型本地已有缓存，但偶尔仍访问外网；Mock 测试全部通过，真实 Agent 却耗尽工具调用次数。

### 回答要点

1. 先读取持久库 Schema、锁定依赖版本和备份状态，确认是否为跨版本格式；禁止在没有迁移规范时原地改写生产索引。
2. 关系库保存权威业务数据，向量库视为可重建派生索引；保留旧目录后按当前版本重建，并核对 collection 数量和抽样查询。
3. 本地缓存加载使用完整 repo ID、snapshot 路径和 `local_files_only=True`；临时修改进程环境必须加锁并保证首次加载 single-flight。
4. `create_all()` 不负责已有表增量升级；迁移要版本化或至少可重入，并验证“旧表升级”和“重复执行”。
5. Tool 参数属于不可信 LLM 输出。对象/字符串、数组混型、别名和范围都要在服务端归一化，失败要计入工具预算和审计。
6. 验证矩阵至少包含真实 MySQL、真实 Embedding、真实模型生成、调度任务、全量后端测试、前端测试/构建和 HTTP smoke；接口 200 不能代替业务终态。

### 面试回答

> 我不会先补 `_type`，因为这可能只是跨版本 Schema 的第一个症状。我会保留旧库，从关系库真源重建派生索引，并把离线模型解析和并发初始化一起修好。之后用真实 Agent 跑到终稿，观察工具调用、审核和异步索引；真实返回若偏离 JSON Schema，就在消费边界归一化并补回归。这样修的是数据安全和完整链路，而不是让启动日志暂时不报错。

## 10. 用户重复点击“生成”，两个 Worker 又同时消费，如何保证只产生一个业务结果？

### 情景

用户点击生成后没有立即看到响应，于是再次点击；网关也因超时重试了一次。队列采用 at-least-once 投递，同一消息又被两个 Worker 同时取到。任务内部还会保存终稿、写向量索引并调用第三方发布接口。

### 回答要点

1. 先按副作用拆分幂等域：创建任务、执行 Agent、保存终稿、索引记忆和第三方发布不能共用一个模糊的布尔状态。
2. 创建入口接收客户端 key，以 `(user_id, operation, idempotency_key)` 建联合唯一约束并保存请求 hash；相同 key、不同 payload 返回冲突。
3. “先查 pending 再改 processing”存在竞态。Worker 用条件 UPDATE、行锁或带过期时间的数据库租约原子认领，只有认领成功者执行。
4. 每个副作用使用稳定 execution/event key，数据库落库用唯一约束或 upsert；完成结果持久化，重复请求直接回放或返回已有资源。
5. 业务事务和消息发布用 Transactional Outbox 消除提交窗口；消费者仍按 event ID 建幂等账本，因为 Outbox 允许重复投递。
6. 外部发布或扣款要向下游透传幂等键并保存平台业务 ID。调用超时但结果不确定时先查询，不能自动重放造成重复投稿或扣款。
7. 测试至少覆盖顺序重复、并发重复、同 key 不同参数、Worker 崩溃租约回收、外部调用成功但本地记录失败，以及多租户使用相同 key。

### 面试回答

> 我不会承诺消息只投递一次，而是假设入口、队列和 Worker 都可能重复。入口用用户作用域的幂等键和请求摘要复用首次结果；Worker 用数据库条件更新或租约原子认领；各 step 用 execution key 和唯一约束防重复落库；业务事务通过 Outbox 可靠地产生事件，下游按 event ID 去重。第三方副作用还要透传幂等键或保存平台 ID，结果不确定时查询或人工核对。这样得到的是 at-least-once 传输下的业务效果幂等，而不是夸大成端到端 exactly-once。

### 项目落地状态

本项目已在记忆反馈中使用用户级联合幂等键，在终稿索引中实现 Outbox、数据库租约、有限重试和向量 upsert，并有并发消费与跨租户碰撞测试。创建 Agent 任务仍没有入口幂等键，长任务仍依赖 `BackgroundTasks`，生产多 Worker、进程故障注入和第三方发布结果不确定窗口尚未验证。

## 11. 发布后 MySQL 报 ORM 字段不存在，多个实例还会同时启动迁移，怎么办？

### 情景

代码给 `tasks` 新增了 `execution_status` 等列，SQLite 新库正常，已有 MySQL 却报 1054。启动脚本调用了 `create_all()`，迁移 SQL 还写了 `ADD COLUMN IF NOT EXISTS`；两个应用实例同时启动时偶发 DDL 冲突。

### 回答要点

1. 对照 ORM、目标库 `information_schema` 和迁移历史确认 Schema 漂移；`create_all()` 不负责旧表 ALTER。
2. 在目标 MySQL 版本真实执行迁移，不能用 SQLite 成功证明 MySQL 方言兼容；先用 RED 测试固定旧表升级行为。
3. 迁移必须可重入：已存在列跳过，缺失列执行标准 ALTER，失败后允许从已完成步骤继续。
4. `information_schema` 的先查后改不是原子操作；由单一迁移 Job 执行，或用同连接 advisory lock 串行化完整序列。
5. 验证不仅看脚本退出码，还要连续执行两次、检查实际列，并重跑触发错误的原始 ORM 查询。
6. 生产使用 Alembic 等版本表管理 upgrade 顺序；应用启动只检查版本，避免每个 Web Worker 自动 DDL。

### 面试回答

> 我会把它当作 Schema 发布流程故障，而不是给查询临时删字段。先确认 `create_all()` 的边界和目标 MySQL 方言，再把迁移改成可重入升级；对于多个实例，用单迁移者或同连接 named lock 消除检查与 ALTER 的竞态。验证要在真实目标库连续跑两次，并执行原始 ORM 查询。轻量脚本能救当前环境，但生产最终要进入带版本表、发布顺序和回滚预案的迁移体系。

## 13. 接口 404 后 React 页面开始无限请求，怎么定位？

### 回答要点

1. 分别直接请求后端和经过前端代理请求，区分路由缺失与代理错误。
2. 对照运行中 OpenAPI 和当前源码；源码有路由但 OpenAPI 没有，优先怀疑旧进程未重启。
3. 从 Network 调用栈回溯 `useEffect`、`useCallback` 和 Context Provider，检查依赖引用是否每次渲染都变化。
4. 错误 Toast、全局 loading 和日志状态都可能成为反馈环：请求失败更新全局状态，全局状态重建依赖，Effect 再请求。
5. Provider 函数使用 `useCallback`，Context value 使用 `useMemo`；失败测试断言请求次数而不只断言错误文案。

### 面试回答

> 404 是触发器，不是无限循环本身。我会先确认运行后端是否注册路由，再沿 React 调用栈找谁重新触发 Effect。若 Toast Provider 每次渲染都创建新 value，失败提示就可能改变回调依赖并再次请求。我会同时修运行版本和引用稳定性，并补 404 场景的请求次数断言。

## 12. 任务列表越来越慢，而且并发重试会重复执行，怎么系统排查？

### 情景

任务表从几千行增长到几百万行。接口按用户、状态和创建时间查询最近 20 条任务，响应从 50 ms 变成 2 秒；ORM 序列化时还会逐条查询用户。与此同时，用户连续点击两次重试，两个 Worker 都把同一个任务改成处理中。

### 回答要点

1. 先拆成查询性能和并发正确性两个问题，不能用“加 Redis”同时掩盖。
2. 打印或采集 ORM 最终 SQL，用慢查询日志与 `EXPLAIN` 检查扫描行数、索引、排序和临时表；避免 `SELECT *`。
3. 为真实查询模式评估 `(user_id, status, created_at, id)` 等联合索引，字段顺序由等值过滤、范围、排序和数据选择性决定，不能机械套模板。
4. 处理 N+1：使用 `selectinload`、`joinedload`、批量查询或直接投影必要字段；结合分页检查 JOIN 是否造成重复行。
5. 深分页改用包含 `created_at + id` 的游标分页；保留稳定唯一排序，避免新增数据导致重复和漏项。
6. 重试认领不能“先 SELECT 再 UPDATE”。使用 `UPDATE ... WHERE status='awaiting_human'` 的条件更新，检查影响行数，或使用版本号乐观锁。
7. 每个请求使用独立 Session；事务只包住短小数据库操作，不在持锁期间等待 LLM。死锁只对幂等且可安全恢复的数据库事务做有限重试。
8. 优化后在接近生产的数据量和并发下复测 P95/P99、扫描行数、锁等待、连接池等待与写入代价。

### 面试回答

> 我会先用最终 SQL、慢查询和 EXPLAIN 证明慢在哪里，再针对查询形状设计联合索引，解决 N+1 并将深 OFFSET 改成游标分页。正确性方面不依赖查询后再修改，而是用带旧状态条件的原子 UPDATE 或版本号认领，只有影响一行的请求获得执行权。事务保持短小，模型调用放在事务外。最后同时验证读延迟、写入成本和并发下只产生一个执行者。

### 项目联系与验证边界

本项目已经使用 SQLAlchemy、MySQL、请求级 Session，并在部分恢复/租约链路采用条件更新、版本或数据库锁；现有活文档也记录了 MySQL Schema 迁移修复。但本题中的百万级数据、深分页和性能提升属于通用设计练习，本轮没有构造百万行数据或运行数据库基准，不能写成项目已经实现的性能收益。
## 14. 运营导入 1000 篇爆文，是否直接让 LLM 总结成一张风格卡？

### 情景

运营团队整理了 1000 篇高点赞文章，希望一次性喂给模型，自动覆盖线上风格卡，并以导入数量作为“学习效果”。文章来自不同作者、时间、类目和平台，部分是同一热点的转载。

### 回答要点

1. 先区分事实知识与表达风格；具体人物、数据和案例进入知识库或去标识化，风格卡只保存结构、节奏、钩子、论证和 CTA。
2. 绝对点赞存在曝光、时间、作者和类目偏差；按平台/类目/时间标准化，缺少曝光分母时只能作为弱信号。
3. 做 URL/content hash/语义近重复、授权与完整性检查，并限制单作者和单热点占比，避免重复内容形成虚假多数。
4. 每篇独立抽取严格 Schema 特征并保存模型/Prompt 版本、证据、置信度和失败状态；批量任务支持部分成功、有限重试和幂等。
5. 按平台、内容类型、受众和主题聚类；聚合时统计支持率、分位数、离群点、可选变体与反例，不能简单平均或选第一篇。
6. 产出 candidate StyleCardVersion，不得直接覆盖 active；用留出 Brief 对照生成并检查风格符合、事实性、合规、来源近似风险和多样性。
7. 人工审核后小流量发布；线上采用、编辑和发布指标达到最小样本量才更新权重，并保留回滚。

### 项目落地状态

项目已有按关键词取 1～3 篇高点赞文章的离线脚本、结构化规律抽取、去标识化、Prompt 注入边界、连续文本重叠检查和 StyleCardVersion。尚缺学习 Batch/Item、逐篇特征表、语义去重、多样化采样、候选审核和留出集评测，因此当前只能称为批量脚本雏形，不能称为生产级批量学习平台。
